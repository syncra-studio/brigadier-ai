## The speed levers, measured on T1

T1 (`tools/ab/tasks/t1.md`, "Sidebar hide mode") re-ran on a dev daemon from `f2d40e0d`, with normal
routing and the thread on Opus high, from a warm clone (`tools/ab` clone/warm/recorder/send/times).
One run, so the numbers carry its variance.

| Stage | Demo (before) | This branch (after) |
| --- | --- | --- |
| Submit → the lead's `delegate_task` | 47 s | **25.1 s** |
| The worker, start → report | 7m 20s | **8m 55s** (535 s) |
| … of which after the review came back | 3m 41s (after a clean review) | **4m 50s** (290 s, after a review with 3 findings) |
| Report → landed → the answer | 31 s | **24.3 s** |
| **Total** | **8m 35s** (515 s) | **9m 45s** (584.8 s) |

**The total missed: 70 s slower than the demo.** Delegating came 22 s sooner and landing 7 s sooner,
but the worker took 95 s longer. Where the worker's time went (its Codex rollout, seconds after
submit):

- 25–81 s: read the code, sent its outline. 81–84 s: waited for the go-ahead (the lead approved
  in 3 s). The plan review ran meanwhile (81–184 s, 6 findings, passed on at 193 s).
- 84–188 s: built it, then called `review_code`. 188–270 s: the code review (3 findings, all P3:
  a token missing from a list, a missing comment, a stale doc line).
- 272–293 s: fixed the three findings.
- 362–519 s: browser smoke checks and screenshots of both modes. The brief's done-when asked for "a
  screenshot of your dev build in both modes", which the worker had not taken before the review.
- 526–560 s: typecheck, lint, tests and build, then `submit_report`.

What the levers did here:

- **(a) Report once green.** The findings message said "once your fixes are committed and the checks
  they touch pass, report at once; don't verify again". The worker spent the time after it mostly
  on a done-when item it still owed (the screenshots), not on checking again. That differs from the
  demo's failure, but the time still sits after the review.
- **(b) Lower effort for small work.** The lead passed no `effort`: the worker ran on Codex at high.
  The brief named five files across the sidebar, tokens and settings, so the lead judged it not
  small. That is the lead's call, as designed.
- **(c) Delegate sooner.** 25.1 s against 47 s, after one `query_brain` and one `code_search`.
- **(d) Fan out.** T1 is one change; nothing to split.

### Run 2, after three fixes

Run 1 missed, so three fixes went in (`e6fa23b7`, THREAD-UX-PLAN.md §4.1): `delegate_task`'s
`effort` is required, with the rule and examples in the thread's instructions; a brief asks for
screenshots only when the user did; a lead worker does its slow evidence before `review_code`.
T1 then ran once more, the same way: same request, base, image and routing, thread on Opus high,
a warm clone, a dev daemon from `e6fa23b7`. "Total" is the first answer in both runs. (Run 1's
request reopened at 10m 27s, when the landing's background review found two things the lead then
fixed by 10m 44s. In run 2 the worker's clean review covered the landed tip, so nothing reopened.)

| Stage | Demo (before) | Run 1 (`f2d40e0d`) | Run 2 (`e6fa23b7`) |
| --- | --- | --- | --- |
| Submit → the lead's `delegate_task` | 47 s | 25.1 s | **25.9 s** |
| The worker, start → report | 7m 20s | 8m 55s (535 s) | **4m 51s** (290.7 s) |
| … of which after the review came back | 3m 41s (clean review) | 4m 50s (290 s, 3 findings) | **29 s** (clean review; writing the report) |
| Report → landed → the answer | 31 s | 24.3 s | **19.3 s** |
| **Total** | **8m 35s** (515 s) | **9m 45s** (584.8 s) | **5m 36s** (336.4 s) |

**Run 2 met the goal: 2m 59s faster than the demo, 4m 9s faster than run 1.** The worker's own time
(timestamps after submit): built from 26 to 147 s; typecheck, lint and tests at 147–153 s; the
brief's screenshots by 218 s; `review_code` at 226 s; the review came back clean at 288 s; the
report followed at 289–317 s with no further checking; landed at 324 s; the answer at 336 s.

What each fix did here:

- **Effort.** The lead named it, as it now must: `"high"`. It judged a persisted two-mode sidebar
  with a menu, five requirements over `sidebar.tsx`, `AppSidebar.tsx` and the components that read
  the sidebar's state, as more than small work. So lever (b) didn't lower this worker's effort.
  It is the lead's call per task. Routing put the worker on Claude Opus this time (Codex in run 1).
  That is the router's choice, and it is a difference between the runs.
- **Screenshots.** The brief still asked for them ("run the app and checked by eye, with
  screenshots saved"). T1's frozen request carries the A/B harness's safety line ("any GUI check
  uses your own dev build…"), which reads as the user expecting GUI checks. The rule didn't stop
  the ask here.
- **Evidence before the review.** This is what moved the time. The screenshots came before
  `review_code`, so after a clean review only the report was left: 29 s against run 1's 290 s and
  the demo's 221 s.
- **Report at once (a).** Nothing was re-verified after the clean review.
- **One cost left.** The worker waited idle 60 s (228–288 s) for its review. Calling `review_code`
  right after the commit and gathering the evidence while the review runs would overlap the two.
  Not built: it reverses fix 3's order and needs the user's call.
