# REA's measured study question (2026-10-11)

SESSION-FIXES-PLAN.md §3 "REA for study tasks", Verify: one frozen study question about an Electron
app's bundle, run once with REA and once without. Gate: worker tokens with REA ≤ 0.5× without, and
both arms reach the written findings, judged by an independent reviewer.

**Result: REA misses the gate.** With REA the worker used 1.12× the tokens of the worker without it,
took longer, and its answer was judged further from the findings. Recommendation: drop REA.

## Setup

- **Target:** the reference app's bundle (app.asar, 567,757,028 bytes, version 26.1007.21159),
  read-only. Its sha256 was `97b8e5fd…87d9fdb` before and after both runs.
- **Rubric:** written and frozen before either arm ran, outside both arms' workspaces. It is
  reproduced below without the app's name.
- **Arms:** one dev `brigadierd` per arm, each with its own scratch data dir and a fresh clone of the
  same one-file project. Both Brain seeds were empty. Each was set up with
  `tools/ab/setup.py --claude-workers opus`.
  - The thread ran on Claude Opus at high effort, on the same account.
  - Both threads got the same request word for word. They were asked to delegate one scout with
    `study: true` and `target` set to the bundle, and to pass it the question.
  - Arm B's daemon ran with `BRIGADIER_REA=off` (debug build), through a wrapper, because
    `tools/ab/startd.sh` clears the environment.
- **Build:**
  - Arm B ran on `00a0b8fc`.
  - Arm A ran on `711c0500`, which only fixes REA's install through a symlinked data dir, a path
    arm B never takes.
  - A first arm A on `00a0b8fc` was thrown away: its install failed (the bug `711c0500` fixes), so
    its worker had no REA.
- **Measured** with `tools/ab/worker_tokens.py`, which reads each arm's data dir read-only.

## What happened with REA

The REA worker used `analyze_javascript_application`, `trace_javascript_semantics`,
`trace_application_feature`, `inspect_analysis_view` and `export_evidence_bundle`. Its own report says:

- `analyze_javascript_application` on the whole 567 MB bundle crashed the server twice.
- The worker then extracted the bundle into its scratch folder and pointed REA at a six-file subset.
- REA doesn't index object fields, so most of the answer was read by hand.
- The exported evidence bundle was 88 MB, over the 8 MB output limit, so it wasn't kept.

The worker without REA read the bundle by hand from the start.

## The findings, judged

One Codex reviewer (`codex exec`, high effort, read-only) judged the two reports against the rubric:

- It didn't know which report came from which arm.
- REA's name and evidence ids were masked in both reports.

| Finding | Without REA | With REA |
|---|---|---|
| F1 central opener and what callers pass | holds | holds |
| F2 right-hand panel, text-editor tab reused, scrolled to the line | holds | partly: says a line opens a read-only review tab instead |
| F3 metadata sample decides; folder or unshowable kind goes to the file manager | holds | holds |
| F4 triggers: file card or reference, diff line, drop | partly: a plain diff-line click opens nothing | partly: same, and drops are missing |
| F5 external target or workspace mode or saved target, plus recents | holds | holds |
| F5 modifier-click skips the panel | holds | holds |
| F5 cloud host opens a review-source tab | partly (HTML only) | partly (HTML only) |
| F5 office files open a dedicated page | holds | holds |
| **Reaches the findings** | **no** (F4) | **no** (F2, F4) |

Both arms independently found that a plain click on a diff line opens nothing, and that opening goes
through a context-menu or modifier action instead. So the rubric's F4 diff-line wording may itself
be wrong. That doesn't change the outcome: the answer without REA was the closer one, and the token
gate fails either way.

## Rubric (frozen before the runs)

> In the app at <target>, in its local agent threads: when the user clicks a file the agent
> mentions (a file card or file reference in a turn, or a line in a code diff), how does the app
> show that file beside the chat, and what decides where and how it opens? Answer from the app's
> bundle: name the modules or functions involved (minified names are fine, with the file they
> are in), the order of the decisions, and what each trigger passes. Paraphrase; quote no more
> than a short identifier.

An arm reaches the findings when F1–F4 hold and at least two F5 items do.

- **F1.** One central opener handles file references from the thread. It is exported as
  openWorkspaceFile, in the app's initial chunk. Callers pass the path, cwd, host, line and column,
  and an "open in side panel" flag.
- **F2.** By default the file opens as a tab in the right-hand side panel, beside the chat
  (target "right"). A text file opens in a text-editor tab keyed by host and path, reused when it
  is already open, and scrolled to the clicked line.
- **F3.** Before picking the viewer, the opener asks the host for the file's metadata with a
  content sample ("read-file-metadata"):
  - a folder goes to the system file manager;
  - a content kind the panel can't show goes to the file manager or an external app instead of
    the panel.
- **F4.** The triggers each call the opener with the open-in-side-panel flag:
  - clicking a file card or file reference in a turn;
  - clicking a line in a code diff, which passes the clicked line;
  - dropping files on the side panel.
- **F5.** Exceptions (any two):
  - an explicit target, the "workspace" open mode or a saved preferred target opens the file in the
    external editor, and records it in the thread's recent files;
  - a modifier-click doesn't take the panel path;
  - files on a remote or cloud host open as a "review file source" tab in the right panel;
  - pptx and xlsx files open in a dedicated office-file page.
