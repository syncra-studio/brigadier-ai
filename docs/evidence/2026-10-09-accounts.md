# Evidence: several accounts per CLI (2026-10-09)

Checked against the installed CLIs: Claude Code 2.1.295 and codex-cli 0.161.0, macOS. Every
probe ran in scratch folders under `/tmp`, without signing in to anything. The user's own
`~/.claude`, `~/.codex` and Keychain were not touched.

## Each home keeps its own login

- `CLAUDE_CONFIG_DIR=<scratch> claude auth status --json` reports `"loggedIn": false`,
  `"authMethod": "none"`. `configDirectory` and `projectsDirectory` both sit inside the scratch
  folder. With the variable unset, the same command reports the user's own login. The fields
  are `loggedIn`, `authMethod`, `apiProvider`, `email`, `orgId`, `orgName` and
  `subscriptionType`. None of them is a credential.
- `CODEX_HOME=<scratch> codex login status` prints `Not logged in`.
- Codex's app-server `account/read` returns `{"account": null, "requiresOpenaiAuth": true}` in a
  scratch home. For a signed-in home the schema gives
  `{"type": "chatgpt", "email": …, "planType": …}`. It returns no token unless `refreshToken`
  is asked for, and Brigadier never asks for it.
- To sign in, a terminal runs the CLI's own `claude auth login` (`--claudeai` is the
  default, per `claude auth login --help`) or `codex login` (`--device-auth` also exists),
  with the account's home set.

## History has to be shared for a switch to resume

**Claude.** A session was written under home A (`-p hi --session-id <uuid>` against a dead
`ANTHROPIC_BASE_URL`, with a fake key so that no login was needed), then resumed:

- home B, whose `projects` is a link to A's `projects`: `--resume <uuid>` found the session.
  It retried the same dead URL, and the transcript grew from A's lines to 44.
- home C, with no link: `No conversation found with session ID: <uuid>`.

**Codex.** `codex app-server` in home A ran `thread/start`, then `turn/start` against a
`model_provider` whose `base_url` is a closed port. That wrote
`A/sessions/2026/10/09/rollout-…-<id>.jsonl`. Then `thread/resume {threadId}`:

- home B, whose `sessions` is a link to A's: success.
- home C, with no link: `no rollout found for thread id <id>`.

## A login variable beats the home's login, and flag settings can blank it

- A project's `.claude/settings.json` with `env.ANTHROPIC_API_KEY` set (under
  `--setting-sources project`) made Claude use that key: it retried the dead base URL instead
  of reporting no login.
- Adding `--settings '{"env":{"ANTHROPIC_API_KEY":"","ANTHROPIC_AUTH_TOKEN":"","CLAUDE_CODE_OAUTH_TOKEN":""}}'`
  gave `Not logged in · Please run /login`. The same happened with the key set in the process
  environment. Flag settings beat project settings, and a blank value counts as none.
- codex-cli 0.161.0's binary names `OPENAI_API_KEY`, `CODEX_API_KEY` and `CODEX_ACCESS_TOKEN`.
  Claude's precedence is documented at
  <https://code.claude.com/docs/en/authentication#authentication-precedence>.

## Codex bindings

`gen-codex` was run against 0.161.0. Its schema differs from 0.159.2 only in how
`CodexErrorInfo` is spelled: the same variants, regrouped so that the generator emits a struct
of flattened options in place of an enum. `account/read`, `account/rateLimits/read`,
`thread/resume`, `Account` and `GetAccountRateLimitsResponse` are the same in both versions.
The 0.159.2 bindings were kept; the adapter tolerates unknown fields.

## Dev build with fake CLIs (2026-10-09)

A dev `brigadierd` ran on a scratch data dir and a scratch `HOME`, with fake `claude` and `codex`
first on its login `PATH`, driven over IPC (`tools/ab/bipc.py`); the debug app (its own bundle
identifier) was then opened on the same data dir. The fakes logged every call with its home.
No real CLI, login, `~/.claude`, `~/.codex` or Keychain item was used.

| Case | Seen |
| --- | --- |
| Own login is account 1 | `getAccounts` listed each CLI's own login (me@example.com, default) before any sign-in |
| Add, rename, default | `addAccount` ran `auth login` / `login` in `accounts/<id>`; the row filled in with that account's email and quota; renaming to "Work" and making it the default went through `updateSettings`, and back |
| Two chats at once | one chat on the own login (no home variable) and one on Work (`CLAUDE_CONFIG_DIR=…/accounts/acct-2233efbd`) answered side by side |
| One-click switch | `updateSetup` with Work, then a message: the CLI started on Work with `--resume` and the chat's session id (`d31a9983…`); the chat kept both earlier messages |
| Limit mid-chat, switching on | the own login's second turn hit its limit; the chat resumed the same session on Work and finished; notice "Claude Code hit its usage limit on me@example.com; continuing on Work." and the pill reads Work |
| Every Claude account limited | the turn ran on Claude, hit the limit, and Codex stood in ("Claude Code hit its usage limit") |
| Switching off | a limit on the own login went straight to Codex; Work was not started |
| Remove | `removeAccount` ran `codex logout` in that account's home and deleted it; the shared Codex history stayed |
| Isolation | every sign-in and sign-out ran inside an `accounts/<id>` home; none ran on the own login |
| Screen | Settings → Accounts (rows, bars, Default badge, Add account, the switch) and the composer's account pill (draft and chat) were captured from the dev app; the pill's menu could not be opened (no pointer events without Computer Use) |
